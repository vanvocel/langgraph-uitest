# LangGraph UI 自动化测试框架 — 设计方案

> 本文档汇总项目边界、流水线、YAML/POM/断言/登录等已确认设定，作为后续实现的契约。

---

## 1. 项目定位

### 1.1 目标

本项目**不负责从需求文档理解业务**。输入是已经写好的**自然语言测试用例**（可由其他 AI 预先生成），本项目负责将其落地执行并产出报告：

1. 将自然语言测试用例转化为方便 AI / 框架读取的 **YAML**
2. 调用 AI **打开真实浏览器**，在对应页面寻找用例所需元素，并保存到 **POM**
3. 用传统自动化测试框架**执行用例**（执行期不调用 LLM）
4. 输出 **Allure** 测试报告

### 1.2 使用场景

面向**需求向测试用例**的执行与举证，而非日常全量回归库的长期维护。

- 每个需求使用**独立的一套 POM**
- 用例随需求生灭，资产按需求归档即可
- 同一批 YAML + POM 可在修 bug 后复跑，对比 Allure 结果

### 1.3 核心原则

| 原则 | 说明 |
|------|------|
| AI 写资产，框架跑资产 | AI 只参与 NL→YAML、寻元素写 POM；执行期无 LLM |
| 绑定与执行分离 | locator 未通过校验不得写入 POM，不得生成“假可跑”脚本 |
| 意图稳定，定位可重生 | YAML 用语义元素名；locator 可按需求重绑 |
| 不确定就澄清/阻塞 | 低置信度、绑定失败标 `blocked`，不硬跑 |

## 2. 总体流水线

```text
自然语言测试用例（精简、步骤尽量详细）
        │
        ▼
① NL → YAML
   AI 理解动词并自主修正，归一到标准 action / assert 白名单
        │
        ▼
② 寻元素 → POM（每需求一套）
   通用登录前置 → AI 打开浏览器实际查找 → 校验通过才写入
        │
        ▼
③ 传统自动化框架执行
   按步骤调用 tool（POM 设计模式）
        │
        ▼
④ Allure 报告 + 结构化日志
```

### 2.1 LangGraph 职责范围

LangGraph 编排**生成侧**（及可选的失败后重绑），不编排日常执行主路径：

```text
parse_to_yaml
  → collect_needed_elements
  → bootstrap_login（通用登录）
  → open_page_and_discover（可循环多页）
  → validate_and_write_pom
  → END
```

执行与报告：

```bash
pytest ... --alluredir=allure-results
allure serve ...
```

## 3. 目录与产物约定（建议）

按**需求**隔离资产：

```text
runs/{requirement_id}/
  nl/                 # 原始自然语言用例
  yaml/               # 结构化用例
  pom/                # 本需求 POM（locators + 可选业务封装）
  bindings/           # 可选：元素绑定元数据、置信度
  allure-results/
  logs/
  summary.json
```

全局可复用部分（跨需求）：

```text
framework/
  tools/              # 基础操作与断言 tools
  bootstrap/          # 通用登录等
  toast/              # 全局 toast 监听与判定规则
config/
  accounts.yaml       # 账号引用（不含明文密码）
  settings.yaml
```

密码等密钥放环境变量 / CI Secret，YAML 只引用 `account_ref`。

## 4. NL → YAML

### 4.1 输入约定

- NL 尽量**精简**，步骤不宜过多
- 每个步骤尽量**详细**（操作对象、数据、期望结果写清）
- **不要求** NL 使用固定动词（「点一下」「保存看看」等均可）

### 4.2 AI 职责

- 理解自然语言并**自主修正/归一**
- 输出符合 schema 的 YAML
- 将随意动词映射到**标准 action 白名单**
- 根据期望结果选择正确的 toast 断言意图（见第 7 节）
- 映射不确定时标记 `needs_review`，不输出半吊子步骤

### 4.3 YAML 层必须标准化

NL 层动词随意；**YAML 层 action / assert 必须是白名单**。执行器只认 YAML 标准字段，不认自然语言。

动作白名单（示例，实现时可扩展）：

- 操作：`open` / `click` / `fill` / `select` / `hover` / `upload` / `wait_visible` …
- 断言：见第 7 节断言工具箱

可选前置：

```yaml
preconditions:
  - auth: logged_in
setup:                    # 可选：造数、切角色等
  - ...
```

## 5. 登录与通用前置

### 5.1 结论

登录做成**通用提前步骤**，不要求每条 NL 都写登录。

寻元素阶段与执行阶段**共用**同一套 bootstrap 登录逻辑。

### 5.2 配置形态（示意）

```yaml
bootstrap:
  login:
    enabled: true
    account_ref: "default_tester"   # 密钥侧解析用户名密码
    land_url: "/home"               # 可选：登录后落点
```

用例侧只声明需要已登录：

```yaml
preconditions:
  - auth: logged_in
```

### 5.3 实现建议

- 登录成功后可保存 storage state / cookie，同需求多用例复用（也可配置为每条重登）
- 验证码 / 滑块 / 短信：测试环境关闭、固定码，或预置已登录态；否则会卡死整条链

## 6. 寻元素 → POM

### 6.1 流程

1. Bootstrap 登录系统
2. 按 YAML 打开相关页面
3. AI 基于真实页面（优先 ARIA / 可访问性树，必要时 DOM + 截图）提出候选 locator
4. **浏览器实测校验**通过后，写入**该需求 POM**
5. 未通过则不写 POM，用例/步骤标记未绑定（`blocked` / `BIND_ERROR`）

### 6.2 校验门禁（避免无效脚本）

未通过门禁**不得**写入 POM，也不得当成可执行脚本交付：

1. 同一语义元素给出多策略候选（如 role+name、testid、稳定 id、css）
2. 实测：可见、可交互、匹配数量符合预期（如唯一）
3. 置信度低于阈值 → 不写入，可人工抽检（如元素高亮截图）
4. 执行期不调 LLM；locator 失效记绑定失败，可单独重跑寻元素修复 POM

### 6.3 POM 范围

- **每个需求一套 POM**，与其他需求隔离
- Toast、登录等跨需求能力放在**框架级全局组件**，不写进各需求 POM

### 6.4 选择器优先级（建议）

`data-testid` > `role + name` > 稳定 `id` > 语义 CSS > XPath（最后手段）

## 7. 执行模型：POM + Tool

### 7.1 结论

页面元素操作按 **POM** 组织；所有操作与断言做成一个个 **tool**。  
执行时根据 YAML 步骤调用对应 tool，**不调用 LLM**。

```text
YAML step
  → 解析 action / element / value / observe(after)
  → 从本需求 POM 解析 locator
  → 调用基础 tool
  → 在观察窗内收集 toast / 导航等结果并判定
  → 写日志 + Allure step
```

### 7.2 两层拆分

| 层级 | 内容 |
|------|------|
| 框架级 tools | `open_url`、`click`、`fill`、`select`、toast 监听与断言、等待等 |
| 需求 POM | 本需求元素 locator；可选少量业务封装（内部仍组合基础 tools） |

## 8. 断言设计

### 8.1 断言工具箱（可扩展）

| 类型 | 用途 |
|------|------|
| `expect_toast` | 期望出现某类/某文案 toast |
| `expect_no_error_toast` / `forbid: error` | 观察期内不应出现**错误级** toast |
| `expect_no_toast` | 完全不应出现 toast（少用） |
| `assert_visible` / `assert_hidden` | 弹窗、抽屉、区块 |
| `assert_text` / `assert_text_contains` | 文案 |
| `assert_count` | 列表条数、筛选结果等 |
| `assert_value` | 输入框/下拉当前值 |
| `assert_enabled` / `assert_disabled` | 可点性 |
| `assert_url` / `assert_title` | 跳转类 |

业务上还关注：按钮点击后是否出弹窗、下拉选择后是否出现对应数据等——用可见性、条数、文案等断言表达。

### 8.2 Toast：出现 ≠ 失败

系统常见：进入页面、筛选、保存等操作需要关注 toast，但：

- **期望结果可以是「出现 toast」**（成功提示，或用例本身就要测错误提示）
- **不能**简单规定「有 toast 就算失败」
- 失败仅针对：出现了**禁止**的级别/文案，或**期望的 toast 未出现**

建议区分 toast 级别（可配置）：如 `error` / `warning` 为错误级，`success` / `info` 为提示级。

### 8.3 短生命周期 Toast + 组合断言

Toast 显示时间短；若「点击后跳转新页面」同时又要看 toast，**不能**等跳转完成再回头查 DOM。

正确模型：**先挂监听，再操作，在观察窗内并行收束**。

```text
① 挂上 toast 监听（或开始录制 toast 事件）
② 执行 click / 其他操作
③ 同一观察窗内并行等待：
     - toast 条件（expect 与/或 forbid）
     - 导航条件（URL / 关键元素）
④ 汇总判定
⑤ 取消监听
```

错误顺序：

```text
click → 等新页面就绪 → 再找 toast   ❌ toast 往往已消失
```

### 8.4 步骤级「观察窗」YAML 示意

```yaml
- action: click
  element: 提交按钮
  observe:
    window_ms: 5000
    toasts:
      - expect: success
        contains: "提交成功"    # 可选
      - forbid: error           # 窗内禁止错误 toast
    navigation:
      expect_url_contains: "/order/detail"
```

默认策略（可被单步覆盖）：

```yaml
defaults:
  on_action:
    observe:
      forbid_toast_levels: [error]
      window_ms: 3000
```

当用例**期望**出现错误 toast 时，覆盖默认 forbid：

```yaml
- action: click
  element: 保存按钮
  observe:
    toasts:
      - expect: error
        contains: "名称不能为空"
    forbid_toast_levels: []
```

### 8.5 组合判定表示意（点击跳转 + toast）

| 期望成功 toast | 错误 toast | 跳转 | 结果 |
|----------------|------------|------|------|
| 要求且出现 | 无 | 正确 | 通过 |
| 要求但未出现 | 无 | 正确 | 失败：缺期望 toast |
| 任意 | 有（且未 expect） | 即使跳转正确 | 失败：错误 toast |
| 出现 | 无 | 不符 | 失败：跳转不符 |
| 不要求成功 toast | 无 | 正确 | 通过 |

原则：**跳转正确也不能吞掉未期望的 error toast**；**写了 expect toast 却没捕获到也不能算过**。

### 8.6 Toast 捕获实现建议

- **优先**：对全局 toast 组件做事件/DOM 监听，将 `{type, text, ts}` 记入内存队列，断言读队列（不依赖 toast 仍挂在 DOM）
- **兜底**：click 前注册 locator 等待，与 URL 等待并行竞态
- 跳转使用显式 URL/关键元素等待，避免依赖固定 `sleep`

## 9. 失败归因、日志与 Allure

### 9.1 失败分类

| 类型 | 含义 |
|------|------|
| `BIND_ERROR` | 元素未绑定 / 定位失败 |
| `UI_ERROR_TOAST` | 出现未期望的错误级 toast |
| `ASSERT_FAIL` | 弹窗、文案、条数、跳转等断言失败 |
| `ENV_ERROR` | 登录失败、页面 500、环境不可用 |
| `NEEDS_REVIEW` | NL→YAML 或绑定时不确定，需人工 |

### 9.2 日志应记录的内容

断言或步骤失败时至少包含：

- `case_id`、`step_index`、`action`、`element`
- 断言类型、期望值、实际值
- 观察窗起止时间
- 窗内捕获到的**全部** toast 列表（level、文案、时间）——即使界面上已消失
- 当时 URL、时间戳
- 截图路径；可选 DOM 摘要 / console error

双通道：

- **结构化日志**（如 JSON line）：便于追溯与分析
- **Allure**：步骤树 + 附件（截图、toast 列表等）

## 10. 技术选型（建议）

| 层级 | 建议 |
|------|------|
| 编排（生成侧） | LangGraph |
| 浏览器（寻元素 + 执行） | Playwright（ARIA/快照、登录态复用友好） |
| 测试运行 | pytest + 自研/薄封装 runner（步骤→tool） |
| 报告 | allure-pytest |
| LLM | 仅用于 NL→YAML、寻元素候选；执行期禁用 |

## 11. 已确认设定清单（速查）

1. **不在本项目做需求理解**；输入是已有 NL 测试用例。
2. **NL 精简、步骤详细**；动词不固定，由 AI 归一到 YAML 白名单。
3. **寻元素**：AI 打开真实浏览器查找；须校验门禁，降低无效脚本。
4. **每个需求一套 POM**。
5. **执行期不使用 LLM**，走传统自动化框架。
6. **登录做成通用前置**；账号用 `account_ref`，密钥外置。
7. **操作与断言 tool 化**，执行按步骤调用；POM 管本需求元素。
8. **Toast**：区分 expect / forbid；出现 toast 不等于失败。
9. **短 toast + 跳转**：先监听再操作，观察窗内并行判定。
10. **失败要有原因分类 + 结构化日志 + Allure**，保证可追溯。
11. **Setup/造数**可作为 YAML 可选能力，后续实现。

## 12. 待实现时拍板的细节

1. Toast 的 DOM/级别识别规则（与前端组件对齐）
2. 同需求多用例：共享登录态 vs 每条重登
3. 默认是否几乎每个操作都 `forbid: error`（建议默认开启，单步可覆盖）
4. 「下拉后出对应数据」默认断言到「有数据」还是「特定文案」（NL 写清最稳）
5. 验证码等特殊登录的测试环境策略
